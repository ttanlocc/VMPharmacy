In `handleCheckout` (around line 197), the current `flatMap` produces separate entries when the same drug_id appears multiple times (e.g., a template with two rows for drug A, or a standalone drug A plus a template also containing drug A). Fix this by adding a merge step after flattening.

1. Takes the `flattenedItems` array
2. Groups by `drug_id`
3. For items sharing the same `drug_id`: sum their `quantity` values, concatenate their `note` values (joined with "; ", filtering empty)
4. Produces a new array of unique-by-drug_id items

The merge should happen BEFORE the `validItems` filter (line 214). Replace the simple flatMap result with the merged result.

Implementation pattern:
```typescript
// After flatMap, merge duplicates
const mergedMap = new Map<string, { drug_id: string; quantity: number; note: string }>();
flattenedItems.forEach(item => {
  if (!item.drug_id) return;
  const existing = mergedMap.get(item.drug_id);
  if (existing) {
    existing.quantity += item.quantity;
    if (item.note) {
      existing.note = [existing.note, item.note].filter(Boolean).join('; ');
    }
  } else {
    mergedMap.set(item.drug_id, { ...item });
  }
});
const mergedItems = Array.from(mergedMap.values());
```

Then use `mergedItems` instead of `flattenedItems` for the `validItems` filter and onward.

Do NOT change the flatMap itself — keep it for the initial expansion. The merge is an additional step.

Two issues to fix:

**Issue A — loadInitialState effect re-runs excessively (app/checkout/page.tsx)**

The `loadInitialState` useEffect (line 59) has `[templateIdParam, customerIdParam, isGuestParam, customer, items.length]` as dependencies. Including `customer` causes it to re-run after it sets customer, creating a potential loop (mitigated only by the `customer.id !== customerIdParam` check). And including `items.length` causes re-runs on cart changes.

Fix: Remove `customer` and `items.length` from the dependency array. Instead, use refs or read current state inside the effect. Specifically:
1. Remove `customer` from deps — use a ref (`customerRef`) that tracks the current customer, or read from localStorage directly to check if customer is already set
2. Remove `items.length` from deps — use a ref (`itemsLengthRef`) or read localStorage

Simplest approach: convert to a one-time initialization effect that runs only on mount (empty deps `[]` or only URL param deps `[templateIdParam, customerIdParam, isGuestParam]`). The URL params don't change during the component lifecycle, so this is safe. Inside the effect, read current state from localStorage directly (via `JSON.parse(localStorage.getItem('vmp_checkout_state'))`) rather than depending on React state.

**Issue B — clearCheckout then setCustomer race in new/page.tsx**

In `handleSelectTemplate` and `handleSelectEmpty` (new/page.tsx lines 52-56, 58-84), the pattern is:
```
clearCheckout();        // sets customer to null + removes localStorage
if (customer) setCustomer(customer);  // sets customer back
```

This works because React batches these, but it's fragile. The `clearCheckout` function removes the localStorage entry entirely (line 129 of CheckoutContext), then `setCustomer` triggers the save effect to write it back. This is fine with React 19 batching.

However, verify that clearCheckout's `localStorage.removeItem` (line 129) doesn't cause the save effect to write `{items: [], customer: null}` before the setCustomer call takes effect. Since the save effect runs after the render (not synchronously), and React batches `clearCheckout` + `setCustomer`, the final state should be `{items: [], customer: customerData}` — which is correct.

If batching is confirmed safe (it is in React 19), no change needed for Issue B. Just add a comment in both `handleSelectTemplate` and `handleSelectEmpty` explaining the batching dependency:
```
// React 19 batches these updates — customer is restored before the save effect runs
```

Focus effort on Issue A — the dependency array fix is the real reliability improvement.
